# Notion Governed Fronting Showcase

This example demonstrates ANIP in front of the Notion API. Agents see governed workspace capabilities, not raw page/database operations.

## Source

- Source spec: `docs/examples/notion-fronting-showcase/source-spec.md`
- CLI starter: `docs/examples/notion-fronting-showcase/anip-fronting-starter.json`
- Package bundle: `registry-packages/notion-fronting-showcase-0.2.0.anip-package.json`

## Generate From Starter

```bash
cd packages/go
go run ./cmd/anip fronting scaffold \
  --starter ../../docs/examples/notion-fronting-showcase/anip-fronting-starter.json \
  --target python \
  --dependency-source local \
  --custom-code-bundle ../../examples/showcase/notion_fronting/custom-code-bundles/notion_fronting_python \
  --transport http,stdio \
  --output ../../examples/showcase/notion_fronting/generated/studio_notion_fronting \
  --force
```

## Live Notion Tests

The smokes need a Python service generated by the current, fail-closed
generator; the checked-in `generated/language-parity/python` service predates
it. The 0.2.0 package bundle predates `package_execution_signature`, so generate
from its service definition:

```bash
cd packages/go
go run ./cmd/anip generate \
  --definition ../../examples/showcase/notion_fronting/registry-packages/notion-fronting-showcase-0.2.0-service-definition.json \
  --package-name notion_governed_fronting_showcase \
  --target python \
  --dependency-source local \
  --custom-code-bundle ../../examples/showcase/notion_fronting/custom-code-bundles/notion_fronting_python \
  --transport http,stdio \
  --output ../../examples/showcase/notion_fronting/generated/studio_notion_fronting \
  --force
```

```bash
export NOTION_TOKEN="ntn_..."
export NOTION_WORKSPACE_SCOPE="<stable-workspace-policy-label>"
export NOTION_PARENT_PAGE_ID="<page-id-shared-with-the-integration>"
export NOTION_DATABASE_ID="<database-id-shared-with-the-integration>"
export ANIP_NOTION_ALLOWED_WORKSPACES="<same-workspace-policy-label>"
export ANIP_NOTION_ALLOWED_PARENTS="<same-parent-page-id>"
export ANIP_NOTION_ALLOWED_PAGES="<same-parent-page-id>"
export ANIP_NOTION_ALLOWED_DATABASES="<same-database-id>"
PYTHONPATH="<repo python packages>:<generated src>" \
  python examples/showcase/notion_fronting/scripts/live_smoke.py
```

`NOTION_WORKSPACE_SCOPE` is the ANIP policy label used by the showcase
adapter. It can match the Notion workspace display name, but the important
property is that it also appears in `ANIP_NOTION_ALLOWED_WORKSPACES`.

The live smoke never mutates Notion: it sets `ANIP_NOTION_ALLOW_MUTATION=false`.
It sets the generated service's `ANIP_API_KEYS_JSON`, with one API key per actor
the 0.2.0 policy bindings select. The generated policy refuses a principal no
binding selects, so the old `dev-admin-key`, which carries no actor claim, no
longer works. The smoke checks that:

- `notion_governance_reviewer`, whose bindings allow everything, gets reads and
  previews for all five capabilities, and `governed_notion_requester` can query
  the database;
- `governed_notion_requester` gets `approval_required` with an
  `approval_request_id` on page creation and page updates; a token without
  `approver:<capability>` scope cannot grant it; `notion_change_approver`
  issues a one-time grant through `POST /anip/approval_grants`; and the
  requester's second invocation, carrying the top-level `approval_grant`,
  returns a preview with `mutation_performed: false`;
- a principal without an actor claim and an actor no binding names are denied,
  and the requester's deny bindings refuse it comments and workspace search.

Run the page-creation smoke only against a disposable parent page:

```bash
export ANIP_NOTION_ALLOW_MUTATION=true
PYTHONPATH="<repo python packages>:<generated src>" \
  python examples/showcase/notion_fronting/scripts/approved_page_smoke.py
```

The approved page smoke invokes `notion.page.create.prepare` as
`governed_notion_requester`, whose binding requires approval, and expects
`approval_required`. `notion_change_approver` then issues a one-time grant through
`POST /anip/approval_grants`, and the requester resubmits the same parameters with
the top-level `approval_grant`. The adapter creates the page only on that granted
invocation.

## Design Point

The backend is the Notion API for this showcase. The ANIP contract owns workspace scope, page/database allowlists, approval posture, bounded `backend_options`, denial rules, and audit.
